# 异步生成队列与模型 TTL 缓存设计

## 背景与目标

当前每次图片生成都会临时创建 `MfluxService` 并加载模型。对于单 GPU 的 Mac，这会让连续生成反复承担模型加载成本。生成请求还是同步 HTTP 调用，多个用户提交时无法明确排队，浏览器也可能因长时间等待产生焦虑。

本设计维持 Flask、Alpine.js、TinyDB 与 mflux 的现有技术栈，不引入 Gunicorn、多进程、Redis、Celery 或其他推理引擎。目标是：

- 单进程、单模型、单 GPU 串行执行图片生成。
- 模型第一次使用时加载，空闲达到 TTL 后自动卸载。
- 生成提交异步化，任务进入 FIFO 队列后立即返回任务标识。
- 前端持续显示排队位置、前方任务数、ETA 和生成状态。
- 任务记录写入 TinyDB，刷新页面后仍可查询；服务重启时不恢复未完成任务。

## 配置

通过 `.env` 提供以下可选配置：

- `MFLUX_MODEL_IDLE_TTL_SECONDS`：模型空闲自动卸载时间，默认 `300` 秒。
- `MFLUX_QUEUE_MAX_SIZE`：允许等待的任务上限，默认 `10`。

非法、空白或非正值配置回退到默认值。队列上限只计算 `pending` 任务；运行中的单个任务不计入等待队列容量。

## 核心组件

### 模型缓存管理器

新增进程内模型缓存管理器，按 `model_id` 保存模型实例和最后一次使用时间。

- worker 开始处理任务时，通过管理器获取模型；不存在时才调用 mflux 构造函数加载。
- 任务完成后更新最后使用时间。
- worker 空闲时检查缓存：超过 TTL 的模型移除强引用，并调用 `gc.collect()`。
- 不调用未经验证的 MLX 专用释放 API；Python 与 MLX 的实际内存归还策略由运行时决定。
- 单 worker 下不会在推理时检查或卸载模型，避免使用中的模型被释放。

### 生成任务管理器

新增 `GenerationTaskManager`，应用进程中只创建一个实例，并启动一个 daemon worker 线程。

- 内存使用 `queue.Queue` 提供 FIFO 调度。
- TinyDB 的 `generation_tasks` 表保存任务元数据和状态。
- worker 一次只处理一个任务；任何生成异常都转为该任务的 `failed` 状态，不终止 worker。
- 每次任务进入终态后，按提交时间仅保留最近 100 条 `succeeded`、`failed` 和 `cancelled` 记录。`pending` 与 `running` 永不被此裁剪逻辑删除。
- 应用启动时清理 TinyDB 中上一进程遗留的 `pending` 和 `running` 任务，不恢复执行。终态记录保留。

任务状态为：

```text
pending -> running -> succeeded
                   -> failed
```

本期不提供取消接口，因此 `cancelled` 仅为后续扩展和裁剪规则预留，不由现有 API 产生。

## API 设计

### 创建任务

`POST /api/generate` 继续接收现有 multipart 或 JSON 字段，完成参数与上传文件校验后创建 UUID 任务并返回 HTTP `202`。

返回数据：

```json
{
  "taskId": "uuid",
  "status": "pending",
  "position": 3,
  "ahead": 2,
  "queueLength": 3,
  "etaSeconds": 90
}
```

队列已满时返回 HTTP `429` 和业务错误码。文件上传在创建任务时保存到临时 uploads 目录，worker 无论成功或失败都会删除该文件。

### 查询单个任务

`GET /api/generate/tasks/<task_id>` 返回任务状态及动态队列信息：

- `pending`：`position`、`ahead`、`queueLength`、`etaSeconds`。
- `running`：状态、开始时间与等待/生成中的耗时。
- `succeeded`：文件名、图片时间戳、推理耗时和生成参数。
- `failed`：对用户安全的错误消息及参数。

任务不存在时返回 API `404`。生成页将其解释为服务重启造成的未完成任务，而不是无限轮询。

### 查询队列

`GET /api/generate/tasks` 返回最近任务清单和队列汇总。任务按提交时间倒序返回，包含提交时间、状态、提示词、模型、尺寸、步数、位置、ETA、结果和失败消息。

ETA 用最近成功任务的推理耗时移动平均乘以前方任务数计算；尚无样本时返回 `null`，前端显示“等待中”。ETA 是提示信息，不作为完成时间承诺。

## 前端设计

生成页提交后立即进入任务状态，不再持有同步生成请求。

- 每秒轮询单任务接口，直到进入 `succeeded`、`failed` 或任务消失。
- pending 显示“第 N 个任务、前方 N 个、预计等待约 X”。
- running 显示“正在生成”和已耗时。
- succeeded 显示现有结果卡片；failed 显示接口错误信息。
- 如果轮询得到 404，显示“服务已重启，任务未完成，请重新提交”。

新增 `/queue` 页面并加入桌面端与移动端导航。页面使用表格展示：提交时间、状态、提示词、模型、尺寸与步数、队列位置/ETA，以及成功图片链接或失败原因。页面在存在 pending/running 任务时每秒刷新；全为终态后停止自动刷新。

## 错误处理与并发边界

- worker 内所有异常必须被捕获并持久化为任务失败，确保后续任务继续执行。
- TinyDB 继续使用现有模块级锁，任务状态的读写和裁剪必须在锁内完成。
- Flask 请求线程只负责创建与查询任务，不直接执行 GPU 推理。
- `position`、`ahead` 与 `queueLength` 是读取时快照；因新任务随时入队，数值允许变化。
- 当前架构只支持单 Flask 进程；多进程会产生多个独立队列和模型缓存，不在支持范围内。

## 测试与验证

- 单元测试：FIFO 执行、队列上限、任务状态迁移、任务失败后 worker 继续、上传文件清理、终态任务裁剪和启动清理。
- 模型测试：同模型连续任务只加载一次；空闲超过 TTL 后下一次任务重新加载。
- API 测试：创建任务返回 `202`、状态查询、队列查询、队列满返回 `429`、未知任务返回 `404`。
- 前端：生成页轮询、队列页渲染与导航入口；执行 `npm run build`。
- 回归：执行 Python 全量单元测试、Python 编译和 `uv lock --check`（环境允许时）。
